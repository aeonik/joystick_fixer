#+title: Branch Recommendations

* Summary

This note records the current branch assessment and recommended next steps for
the repository. The core issue is that several different lines of work were
advanced in parallel and partially overlapped:

- a stable GUI application
- a native JavaFX SVG renderer migration
- XML/controlmap roundtrip experimentation
- packaging and standalone jar fixes

Those goals are individually reasonable, but the repository history shows that
they were not sequenced cleanly.

* Main Recommendation

Use commit =bb031ef= as the behavioral baseline for the GUI, then build a new
stabilization branch from there.

Suggested branch model:

- =product/webview-stable=
  Start from =bb031ef=
  Purpose: stable GUI baseline that preserves known-good behavior
- =research/native-svg=
  Continue from =gui-refactor= only as an experiment
  Purpose: prove native JavaFX SVG rendering can match browser/WebView behavior
- =research/xml-roundtrip=
  Use =stateless= or =sandbox/statefull= as parser/roundtrip research branches
  Purpose: XML transformation and roundtrip experimentation, separate from GUI

Do not continue treating =gui-refactor= as the production truth until the
native renderer clearly matches the older WebView behavior.

- =cljfx.ext.web-view=

That model is less elegant architecturally, but it is coherent. The authored
SVGs rely on browser-like CSS and transform behavior, so the old rendering

* Critique

The repository history shows one recurring mistake:

Architecture changes and rendering-model changes were performed together.

The safer order would have been:

1. split =gui.clj= into smaller namespaces without changing rendering behavior
2. keep WebView as the production path
3. add native SVG rendering behind an explicit experimental path or flag
4. switch only after parity was demonstrated

Instead, the code evolved by:

- splitting namespaces
- changing rendering technology
- adjusting state/reload handling
- fixing packaging/runtime issues

all in overlapping commits. That made regressions harder to localize and left
the repository with multiple partially-realized directions.

* Concrete Recommendation

Short-term direction:

- use =bb031ef= as the stable GUI baseline
- create a fresh stabilization branch from that commit
- cherry-pick only clearly safe non-rendering fixes

Safe candidates in principle:

- standalone jar entrypoint fix
- explicit shutdown/lifecycle fix
- AOT/compile helper cleanup
- path/reload improvements, if they do not change rendering semantics

Do not cherry-pick by default:

- native SVG renderer changes
- fixes that only exist to compensate for JavaFX SVG incompatibilities
- experimental GUI refactors that replace the WebView event model

* Recommended Working Model

Treat the repository as having three distinct efforts:

- GUI Product
  stable app behavior
- Native SVG Renderer Research
  renderer parity and event model experiments
- XML Roundtrip Research
  parser/write fidelity work

Those efforts should not share a single "current truth" branch until they are
better validated.

* Bottom Line

If a single answer is needed:

- last known behaviorally coherent GUI state: =bb031ef=
- latest GUI architecture experiment: =gui-refactor=
- latest XML roundtrip experiment: =sandbox/statefull=
- cleanest XML roundtrip spike: =stateless=

For production progress, stabilize from =bb031ef=.
For renderer research, keep =gui-refactor= experimental.
For XML work, treat =stateless= / =sandbox/statefull= as separate research
tracks.
